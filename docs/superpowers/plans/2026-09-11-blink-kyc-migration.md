# blink-kyc → blinkbitcoin/kyc: migration strategy (approved 2026-09-11)

> Status: approved by Jonas on 2026-09-11. Phase 0 (library) starts first; blink-kyc and blink-mobile phases begin on his go per phase. This is the plan of record; the library PRs it names reference it.


## Context

blink-kyc is Blink's production KYC backend: a Next.js Apollo-federation subgraph (`kyc`) that creates Sumsub applicants, mints one SDK token, hosts a Sumsub Web SDK page at `/webflow`, receives Sumsub webhooks and, on approval, raises the account level through the admin API, sends a notification, and triggers card issuing; a gRPC `GetSumsubShareToken` serves the card issuer. blink-mobile opens that page in a generic WebView with no camera-permission handling and no completion signal; that is the poor user experience (blink-mobile#4246) that motivated the universal library. `blinkbitcoin/kyc` v1 is on main (2026-09-11): `kyc-core`, `kyc-node` (server half), `kyc-service` (deployable), `kyc-react-native` (native Sumsub SDK path + hardened hosted WebView), `kyc-react`.

Goal: rebuild blink-kyc as a thin Blink host over the library, move blink-mobile to the native SDK, delete the old source. Library additions only where universal.

**Decisions taken with Jonas (2026-09-11):** keep blink-kyc as the host repo, rebuilt on `@blinkbitcoin/kyc-node` (Tier A: in-process mint + the sessions domain on Blink's Postgres, no kyc-service deployment); new GraphQL operations, hard cut of `kycFlowStart` / `onboardingFlowStart` / `/webflow`; one-shot migration of `Applicant` into `VerificationSession`, then drop; mobile default = native SDK, library hosted page as fallback and for web clients; names come from the document (the name step and `firstName`/`lastName` go); plain Node server, no Next; Onfido code deleted.

**One thing to be explicit about, because it looks like it contradicts "hard cut":** with a federated router and app builds in the wild, the old operations must stay *callable* until the apps have shipped; what "hard cut" buys is that no new code implements them. The plan freezes the old resolvers under `legacy/` untouched in release N and deletes them in release N+1, once router metrics show no callers. The webhook is the only place both worlds meet, and it falls through to the legacy dispatcher only for sessions the library does not know.

## The quality bar (applies to every phase, every repo; a phase is not done without it)

**Documentation, by consuming role, pedagogic and complete.** Every deliverable ships the page its reader needs, in the reader's vocabulary, with a runnable example and a "what can go wrong" table - the shape `docs/operations/production.md` already has:
- *Mobile developer (blink-mobile):* `docs/identity-verification.md` in blink-mobile - the screen, the two sources and when the fallback triggers, permissions and the OS strings, labels/theme, how to test with the fake source, how to run a sandbox journey on a device.
- *Web developer (otc, terminal, apps):* `docs/integration/consuming.md` + `proxy.md` in the library already cover proxy mode; blink-kyc's README gains "Consuming the subgraph": the four operations, the `flow` enum, the status enum and what each value means for a screen.
- *Backend developer (blink-kyc):* `README.md` rewritten to the kyc/esign front-door shape (what it is → run it locally against the mock provider in five minutes → the ports and policies → testing → deploy), `docs/architecture.md` (the composition over `kyc-node`, one diagram per flow: start, webhook → policies, share token), `docs/policies.md` (what an approval/decline/review means for Blink, the flow catalog, decline reasons), `docs/migration.md` (the Applicant → VerificationSession backfill, what release N and N+1 change, the removal criteria).
- *DevOps:* `docs/operations.md` in blink-kyc - env table with every rename from the old names, the chart values, the migrate/serve entrypoints, the Sumsub dashboard steps, health, the router/supergraph gate, rollback per release.
- *Library maintainers:* each Phase 0 PR updates `docs/architecture/backend.md`, `data-models.md`, `api-contracts.md`, the relevant `docs/integration/*.md`, and the diagrams; `docs/index.md` wayfinding gains "I run sessions with the native SDK" (the session token provider) and "one applicant, many levels".
- *Everyone:* CHANGELOGs come from Conventional Commits (release-please in the library; git-cliff already in blink-kyc's `ci/`), and `docs/upgrading.md` in the library records every breaking change from Phase 0.

**Tests, three tiers, everywhere.**
- *Unit, 100% lines/branches/functions* on every new or touched module in all three repos, enforced by thresholds (the library's Jest/Vitest configs already do; blink-kyc gets Vitest with `coverage.thresholds` at 100 and `scripts/ci/coverage-empty` semantics copied from the library; blink-mobile's jest config gets the new screen and adapters at 100 within the app's existing setup). Silent tests: no console output tolerated (the library's `vitest.setup.ts` / `jest.setup.ts` pattern).
- *E2E mocked, in CI on every PR:* the library's mock provider drives it. blink-kyc: a Postgres-backed suite that boots the host with `KYC_PROVIDER=mock`, runs start → hosted page → self-signed webhook → policy effects observed on fake admin/notifications/card servers (in-process gRPC fakes), plus the migration backfill and the legacy fall-through. blink-mobile: the `createFakeLaunchableSource` path in Jest for the screen, and the Maestro/Detox flow against a mock backend for the hosted fallback.
- *E2E live, opt-in:* the library's `make e2e-live` pattern reused - blink-kyc gets `make test-live` against the Sumsub sandbox (token mint, status, a signed webhook replay, share token), gated by `E2E_LIVE=true` or the `e2e:live` label with the `sumsub-sandbox` environment; blink-mobile's device journeys are the manual matrix documented for release sign-off.
- *Guards as tests:* boundary tests like the library's (`single-write-path`, `provider-boundary`): in blink-kyc, "nothing outside `src/policies/` calls the admin API, notifications or card clients", "nothing outside `src/sumsub/` names Sumsub", "resolvers call the service and mappers only", and the SDL-enum parity test. A convention broken twice becomes a check.

**SOLID and clean code, concretely.**
- Single responsibility: the seven ports listed in Phase 1, each one file, each one reason to change; policies are strategies behind one `VerificationPolicy` interface, selected by a dispatcher - adding a flow is one catalog entry and one policy, never an `if` in the webhook.
- Open/closed and dependency inversion: the host depends on the library's ports (`VerificationProvider`, `SessionStore`, the effects hook), never on Sumsub or Postgres directly; the reactivation decorator and the policies are injected in `composition.ts`, the only file that knows concrete classes.
- Liskov and interface segregation: the gRPC facade and the resolvers see `Pick<VerificationService, …>` of what they use; fakes implement the same narrow interfaces the tests exercise.
- Code smells to refuse in review: duplicated resolvers (today's `onboardingFlowStart`/`kycFlowStart` copy), dispatch by string comparison on env values, side effects inside webhook request handling that can time out the provider, dead variables (today's declined-event `res`), swallowed errors without an audit row, any `console.*` in library or host code (a logger port instead), functions over ~40 lines, modules over ~300 lines, `any`.
- Linting as the floor: Biome + ESLint flat config with the library's rules, commitlint scopes, lefthook hooks, actionlint/shellcheck on CI scripts - copied from the library into blink-kyc in Phase 1 so both repos are held to the same bar.

## What is generic and what is Blink's (the heart of the split)

| Belongs in the library (universal) | Stays in blink-kyc (policy) |
|---|---|
| Sumsub client, signing, token mint, status mapping, webhook verification and parsing | Oathkeeper JWKS auth, the Kratos-user → accountId hop (admin API) |
| Sessions domain, terminal guard, audit log, Knex store, hosted page + bridge, token refresh | The federation subgraph SDL (`ConsumerAccount @key`), the OnboardingStatus enum and its mapping |
| The client component/hook/native source/hardened WebView | Flow → level table (`UPGRADE_LEVEL_TWO`, `CARD`) and what an approval means: account level 2, notifications, card application |
| **New (this plan):** transition effects hook, latest-session-for-user, reject labels on events, applicant-per-user webhook routing, session-aware token provider, Sumsub share token, hosted URL override | gRPC facade for the card issuer, Concourse/chart deployment, decline-reason bucketing, applicant reactivation policy |

## Phase 0 - library additions (blinkbitcoin/kyc), one PR each, 100% coverage, docs in the same PR

Worktrees under `~/Dev/kyc-<topic>` off origin/main; scopes `node` / `core` / `sumsub`? (no: `sumsub` is retired - use `node` for adapter work).

1. **`feat(node): effects.onStatusTransition`** - `packages/kyc-node/src/sessions.ts`: new dep `effects?: { onStatusTransition?(t: StatusTransition & { source: 'api'|'webhook'; rejectLabels?: string[] }) => Promise<void> }`, invoked once, after the store transaction commits, only when `outcome === 'updated'`, inside `applyStatusTransition` (the single write path - so webhook, reconciliation and any future admin path all emit). A throwing effect is logged and audited (`effect_failed`, new `AuditAction`, `errorCode` metadata) and never rolls back the status. Docs: at-least-once; hosts needing exactly-once keep their own outbox keyed on (sessionId, status). `single-write-path.test.ts` extended.
2. **`feat(node): levelName and rejectLabels on WebhookEvent`** - `types.ts` (`WebhookEvent.levelName?`, `rejectLabels?: string[]`), `providers/sumsub/provider.ts` (from `reviewResult.rejectLabels`; the retry/final distinction is already `declined` vs `finallyRejected`), `audit.ts` allow-list gains `rejectLabels`; carried on `StatusTransition` for the effects hook.
3. **`feat(node): one applicant, many sessions`** - Sumsub files one applicant per `externalUserId` across levels; today `VerificationSession.providerApplicantId` is UNIQUE and the webhook resolves by applicant id first, so a second-level session (CARD after L2) would hit the old terminal session and be `rejected_terminal`. Migration `relax_applicant_unique` (drop the unique, add index `(provider, providerApplicantId)`); `SessionStore.getSessionByProviderApplicantId(id, { levelName? })` → newest matching level, else newest non-terminal, else newest; `handleWebhookEvent` tries `(applicantId, event.levelName)`, then latest unbound for the user, then binds. `bindApplicantId` stays bind-once; the mismatch guard becomes "bound to a different applicant". E2E on Postgres: one applicant, two levels, two sessions, both reach their own status.
4. **`feat(node): latestForUser and Query.myVerification`** - `SessionStore.getLatestSessionForUser(userId, provider)`, `VerificationService.latestForUser(userId, { reconcile?: boolean })` (pure read by default: `status()` reconciles every non-terminal read against Sumsub, which is today's call volume on `onboardingStatus`; opt in explicitly), SDL `Query.myVerification: VerificationSessionStatus`, `make codegen`.
5. **`feat(node): hostedUrlFor` and bound status lookups** - `hostedUrlFor?: (sessionId) => string` dep (default unchanged); `getStatusByUserId` returns `{ status, providerApplicantId }` and `status()` binds it, so a session is bound before its first webhook (the share-token RPC needs the applicant id).
6. **`feat(node): Sumsub share token, and the /sdk mint endpoint`** - `createShareToken(applicantId, forClientId, ttlSecs)` on the Sumsub provider handle (a capability next to `getStatusByUserId`, under `providers/sumsub/`, exposed on the `/sumsub` entry); mint via `POST /resources/accessTokens/sdk` with a JSON body (blink-kyc's production-proven call; the query-string form the library uses is Sumsub's legacy shape).
7. **`feat(core): createSessionTokenProvider`** - `packages/kyc-core/src/verification/sessionToken.ts` on the `/hosted` entry: `createSessionTokenProvider({ start: () => Promise<{ sessionId, accessToken }>, refresh: (sessionId) => Promise<string> })` returns a `getAccessToken` that starts once and refreshes after. Without it, wiring the native source's `getAccessToken` (which the Sumsub SDK also calls on expiry) to the start mutation creates a new session row per token expiry and mis-binds webhooks.

Not added: federation directives (host concern; `createKycGraphQL` returns plain `{typeDefs, resolvers}` the host composes with `@apollo/subgraph`), a flow/purpose column (`levelName` on the session plus the host's flow table is enough), applicant reactivation (host decorator over `createSession` using the exported Sumsub client; promote to a capability only if a second host needs it), `expiresAt` on the session payload (only if the library adds it upstream first).

Gate: `make coverage`, `make codegen-check`, `make e2e-backend`, `make e2e-web`, live tier `make e2e-live` for 3 and 6; release-please publishes the four packages. blink-kyc pins those versions.

## Phase 1 - blink-kyc rebuilt as a Blink host (branch `feat/kyc-node-host`, release N)

Runtime: a plain Node server (Fetch-native like `kyc-service`: `@hono/node-server` or the library's `createNodeServer` shape from `examples/serverless-handler-demo`), Apollo Server 5 with `@apollo/subgraph`'s `buildSubgraphSchema`, the gRPC server in the same process, OTel as today. The Dockerfile keeps the chart's contract: port 3000, `/health`, `ENTRYPOINT scripts/entrypoint.sh` with `serve` and `migrate`, `EXPOSE 3000 50060`; `.npmrc` + a Concourse secret for GitHub Packages in the build stage.

Ports, one responsibility each (`src/`):
- `auth/session-verifier.ts` - Oathkeeper JWKS RS256, issuer `galoy.io`, `sub` = Kratos user id (today's `context.ts`, kept).
- `accounts/account-directory.ts` - `accountIdForUser(kratosId)` and `ownerUserIdForAccount(accountId)` over the admin API, cached. **Every library call receives the accountId as "userId"** (it is Sumsub's `externalUserId` and what `Applicant.accountId` migrates into); a host test pins this.
- `flows/flow-catalog.ts` - `KycFlow { UPGRADE_LEVEL_TWO, CARD }` → `levelName` from `SUMSUB_LEVEL_NAME_LEVEL_TWO` / `SUMSUB_LEVEL_NAME_CREDIT_CARD`, and the inverse `flowFor(levelName)` (replaces dispatch-by-level-name in the webhook).
- `status/onboarding-status.ts` - `VerificationStatus → OnboardingStatus`: `initial→NOT_STARTED, incomplete→AWAITING_INPUT, pending→PROCESSING, approved→APPROVED, declined|finallyRejected→DECLINED`; `REVIEW`, `ERROR`, `ABANDONED` stay in the enum (removing values breaks generated clients) and are documented as unreachable.
- `policies/` - `VerificationPolicy { onTransition(t) }` with `AccountLevelPolicy` (admin `accountUpdateLevel(TWO)`), `NotificationPolicy` (approved / declined-with-reason unless final / review started, over the notifications gRPC client), `CardApplicationPolicy` (`TriggerConsumerApplication` with the existing retry ladder, run detached so a slow card service never makes Sumsub retry the webhook), `DeclineReasonMapper` (today's label sets from `app/api/callback/types.ts`), and `PolicyDispatcher` selecting by `flowFor(session.levelName)` and acting only on `source === 'webhook'` (parity with today; reconciliation reads never fire effects).
- `sumsub/reactivation.ts` - decorator over `provider.createSession`: if the user's applicant is deleted, `presence/activated` + `reset` before minting (today's `isApplicantDeleted` path), using the library's exported Sumsub client.
- `grpc/share-token.ts` - `GetSumsubShareToken` over `latestForUser` + `createShareToken`; add an env allow-list of `for_client_id` and note the missing auth as a risk (insecure credentials today).
- `graphql/schema.graphql` + `resolvers.ts` - federated: `ConsumerAccount @key(fields: "id") { onboardingStatus, flowType }` resolved from `latestForUser(accountId)`; the library's operation names kept verbatim so `createProxySource` / `@blinkbitcoin/kyc-react` work unchanged: `verificationSessionStart(input: { platform!, flow: KycFlow!, locale })` → `{ sessionId, provider, status, accessToken, url, allowedOrigin, applicantId }`, `verificationSessionRefresh(sessionId)`, `verificationSession(id)`, `myVerification`. `levelName` is never client-supplied; `flow` maps through the catalog. The library's `Query.health` is not exposed in the subgraph. Old `kycFlowStart` / `onboardingFlowStart` / `firstName` / `lastName` remain in the SDL for release N only, resolved by the frozen legacy code.
- `kyc/composition.ts` - registry with Sumsub only (`defaultRegistry` + `assertProductionConfig`, `KYC_ENV=production`), `createVerificationService({ provider: reactivated(sumsub), store: createKnexSessionStore(knex), publicBaseUrl, effects: { onStatusTransition: dispatcher.onTransition }, tracing })`; routes: `POST /webhook/kyc/sumsub` (library Fetch handler; on `unknown_session` fall through to `legacy/dispatcher`), `GET /hosted/:sessionId` (library handler), `/graphql`, `/health`.
- `legacy/` - `onboarding-flow-start.ts`, `api/callback/**`, `webflow/**` (the Next page becomes a static-served Web SDK page for old apps), `services/db/index.ts`, moved verbatim with a `SUNSET: release N+1` header; **deleted now:** everything Onfido (`services/onfido`, `onfido-*`, `ONFIDO.md`, `onfido-sdk-ui`), `KYC_PROVIDER=onfido` branches in `env.ts`.

Env: add `PUBLIC_BASE_URL`, `KYC_PROVIDER=sumsub`, `KYC_ENV=production`, `SUMSUB_TOKEN_TTL_SECS` (library name; today `SUMSUB_TTL_IN_SECS=1800`; share-token TTL stays 1800 separately); keep `SUMSUB_LEVEL_NAME_*`; chart values renamed in the same release.

Data migration (`services/db/migrations/`): `kyc_library_tables` (calls `runKycMigrations`), then `backfill_applicant_to_sessions`, idempotent (`ON CONFLICT DO NOTHING` on `(provider, providerApplicantId, levelName)`): for each `Applicant` with `origin = 'sumsub'`, one `VerificationSession` with `userId = accountId`, `provider = 'sumsub'`, `providerApplicantId = applicantId`, `platform = 'WEB'`, `levelName` from the applicant's **current Sumsub level** (`Applicant.flowType` is never updated on a second flow, so it mislabels card users), `status` seeded from a one-shot `provider.getStatus(applicantId)` at migration time (seeding `pending` would make the first read reconcile to `approved` and re-fire the approval effects for every existing L2 user), audit `session_migrated`. Runs again in release N+1 before `Applicant` is dropped, so users who started through the legacy op during the overlap are carried over.

Tests: vitest unit at 100% on `src/` (policies, mappers, resolvers, dispatcher, reactivation) with the library's mock provider and memory store; integration against Postgres for the migration and the webhook fall-through; `rover supergraph compose` on the real galoy schema as a `check-code` gate (`yarn generate-supergraph` exists) so a non-composing SDL fails before an image is built; a host test that the SDL's `VerificationStatus` / `VerificationPlatform` enums equal the library's constants; bats reduced to a smoke of `/health` and the webhook.

Gate before release: staging deploy; `docs/operations/production.md` §6 checklist; old and new operations both work through the router; a signed `applicantReviewed` for a migrated approved user answers `unchanged` (no repeated level upgrade or notification); `GetSumsubShareToken` returns a token for a migrated account; Sumsub dashboard subscribed to `applicantCreated`, `applicantPending`, `applicantReviewed`, `applicantOnHold`, `applicantReset` and the production webhook URL `<PUBLIC_BASE_URL>/webhook/kyc/sumsub`.

## Phase 2 - release N to production

Order: migrate job → image → chart PR (the chart copies `schema.graphql`, which recomposes the supergraph) → Sumsub dashboard changes. Parity check: `onboardingStatus` for a sample of accounts equals the live Sumsub status. Router metrics dashboards for `kycFlowStart` versus `verificationSessionStart` call counts become the removal signal.

## Phase 3 - blink-mobile (`feat/identity-verification`)

- Dependencies: `@blinkbitcoin/kyc-react-native`, `@sumsub/react-native-mobilesdk-module` (+ pod), `react-native-webview` to the library's peer range (≥14; today ^13.16). Info.plist: `NSCameraUsageDescription` reworded for ID and selfie capture, add `NSMicrophoneUsageDescription`; Podfile `setup_permissions` gains `Microphone`; Android adds `RECORD_AUDIO` and drops the two Onfido-era lines (`SYSTEM_ALERT_WINDOW`, `READ_EXTERNAL_STORAGE`).
- New `app/screens/identity-verification/identity-verification-screen.tsx`: `IdentityVerification` with `source = createSumsubNativeSource({ getAccessToken: createSessionTokenProvider({ start: verificationSessionStart({ platform, flow }), refresh: verificationSessionRefresh }) })`; on `SDK_UNAVAILABLE` the hosted fallback `createHostedSource({ getSession: start → { url, allowedOrigin }, refreshToken })`; `checkPermissions` via react-native-permissions with `onOpenSettings`; `theme` from the app theme, `labels` from i18n (the existing `CardFlow.PersonalDetails.kyc*` and `FullOnboarding.*` keys, plus new ones); `onComplete` refetches `fullOnboardingScreen` / `personalDetails`; `onError` shows the existing error copy; `onCancel` goes back.
- Replace `useKycFlow` at both entry points (`full-onboarding-flow.tsx` loses the name form and the auto-start on `AWAITING_INPUT`, which with a webhook-fed status would relaunch on every mount; `card-subscription-screen.tsx` starts `flow: CARD`); `card-personal-details-screen`'s "Change KYC information" opens the screen; its `firstName`/`lastName` fields are removed with the name step (names live in the card issuer's own data). Delete `app/hooks/use-kyc-flow.ts` and its spec; the generic WebView screen stays for fiat; `kycUrl` instance config stays only if fiat still needs it, else removed with its allowlist plumbing.
- Tests: jest for the screen (fake launchable source from `@blinkbitcoin/kyc-core/testing`), Detox/Maestro smoke against staging; one real sandbox journey per platform on a device reaching `approved` via the webhook.

## Phase 4 - the other clients

blink-otc-sv-bcr, blink-terminal-app, blink-apps move to `verificationSessionStart` with `@blinkbitcoin/kyc-react` (hosted page in an iframe, proxy mode) in their own PRs. Gate for phase 5: zero `kycFlowStart` calls in router metrics for two weeks after the mobile store rollout.

## Phase 5 - release N+1 (blink-kyc): the deletion

Re-run the idempotent backfill; delete `legacy/`; remove `kycFlowStart`, `onboardingFlowStart`, `OnboardingFlowStartInput/Result`, `firstName`, `lastName` from the SDL; drop `Applicant`; remove `/webflow` and `@sumsub/websdk-react`; chart PR. That is the point at which the old blink-kyc source is gone.

## Risks named, with the mitigation in the plan

- Applicant-per-user vs session-per-level (phase 0.3), token refresh creating sessions (0.7), effects re-firing on migrated users (seeded status + webhook-only effects), stale `flowType` (level from Sumsub at backfill), supergraph composition breaking a rollout (compose gate), GitHub Packages auth in the image build (`.npmrc` + secret), status fidelity (`onHold → pending`, enum values kept), the unauthenticated share-token gRPC (allow-list now, mTLS later), webhook subscriptions the old code never needed (dashboard step), TTL and env renames in the chart, the WebView peer bump.

## Verification, end to end

Library: the repo's gates plus the two new E2E cases (two levels on one applicant; native token provider refresh) and a live sandbox run. Host: unit 100%, Postgres integration for migration + webhook fall-through, compose gate, staging checklist. Mobile: device journeys on iOS and Android with the sandbox, then the router metrics confirming adoption before the deletion release.
